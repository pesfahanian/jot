# Persian (Farsi) support for jot: research report (October 2026)

Full Persian support is feasible on jot's current stack without replacing anything, but two parts of the brief need rethinking. First, a "monospace Farsi editor" isn't a realistic goal: the only Persian monospace font is discontinued, and the right design is proportional Arabic-script glyphs falling back from Source Code Pro. Second, the hard engineering problem is per-block direction detection, which you have to share between editor, preview and PDF. Fonts, letter-spacing and shortcuts are small problems by comparison.

## TL;DR

- **Editor:** use CodeMirror 6's `EditorView.perLineTextDirection` with a viewport-only plugin that sets an explicit `dir` on each line, computed from the first strong character of the *markdown block* with markers, inline code and URLs skipped. Don't rely on CSS `unicode-bidi: plaintext`. Add `bidiIsolatedRanges` for inline code and URLs. Most CM6 shortcuts already work on a Persian layout because CM6 falls back to the key code; your own `keydown` handlers probably won't.
- **Preview/PDF:** run the *same* direction function in a marked post-process. Set `dir` on every block, force code, KaTeX and Mermaid to LTR, and convert list, blockquote and table CSS to logical properties. Font: Vazirmatn (OFL, variable 100–900, `@fontsource-variable/vazirmatn`), loaded only via its Arabic `unicode-range`. Chrome and Firefox already ignore letter-spacing on Arabic. Italic has no Arabic equivalent, so you need to choose a substitute.
- **Review/UI:** build the Farsi rule set on Virastar-style normalisation: ی/ک, digits, ZWNJ around می/ها/تر, «» quotes and Persian punctuation spacing. Treat LLM review as "useful but unproven": the 2026 Persian grammar benchmarks show weak formal-grammar accuracy. Ship Farsi *content* support first, and decide on UI translation separately. A language pack is worth designing now even if only Farsi uses it.

## Key Findings

### 1. CodeMirror 6 and RTL. Confidence: high for the APIs, medium for behaviour details

- **What exists.** `EditorView.perLineTextDirection` landed in @codemirror/view 0.20.0 (2022-04-20). The changelog says it "configures whether the editor reads text direction per line, or uses a single direction for the entire editor". `EditorView.bidiIsolatedRanges` landed in 6.17.0 (2023-08-28), and `bidiIsolates()` in @codemirror/language 6.10.0 (2023-12-28). An infinite-loop bug in bidiIsolates with long bidi lines was fixed in 6.10.2 (2024-06-03), and visual bidi cursor motion was reworked in 6.23.0 (2023-12-28). The reference manual says `textDirectionAt(pos)` returns the direction "as assigned by CSS" and falls back to the global direction outside the viewport. The npm page lists 6.43.12 as the latest @codemirror/view, published around early October 2026. Development has moved from GitHub (archived April 2026) to code.haverbeke.berlin.\[1\]\[2\]\[3\]\[4\]\[5\]
- **There is no `dir="auto"` setting.** CM6 *reads* direction from the computed CSS of each rendered line, so you have to set it with line decorations. Two independent 2026 implementations (Paperling PR #233 and an openchamber PR) both use perLineTextDirection plus viewport-only line decorations. The openchamber PR explains why: a CSS-only `unicode-bidi: plaintext` approach "would leave the computed direction LTR and desync caret/selection drawing (CM6 reads getComputedStyle(line).direction)".\[6\]\[7\]
- **Cursor and selection.** The official bidi example says arrow-key motion is *visual*: Left always moves left. Backspace and Delete are *logical*.\[8\] CM6 runs its own bidi algorithm because "the browser does not give scripts access to the order in which it is drawing the text" (Marijn, discuss.codemirror.net).\[9\] A Chrome-only bug, where clicking at the end of an RTL line put the caret in the wrong place, was reported and fixed on the forum (thread 9571).\[10\] That shows the click-to-position code is still being refined.
- **Markdown marks.** `#`, `-`, `>` and `*` are bidi-neutral, so a line like `- سلام` resolves RTL and the marker renders on the right. **Known breakage:** Joplin's CM6 RTL PR (#10810) reports that list continuation initially puts the new marker on the left even when the rest of the list is right-aligned, and that checked task items stay left-aligned.\[11\] Expect the same here: a freshly continued `- ` line has no strong character yet. Fix it by inheriting direction from the enclosing block (see §2).
- **Mixed lines.** Without isolation, neutral punctuation sticks to whichever side matches the base direction. The CodeMirror docs call the result for code or markup in RTL "an unreadable mess".\[8\] `bidiIsolates()` only isolates nodes that the grammar marks as isolating.\[5\] I couldn't confirm that `@lezer/markdown` marks any, so assume you need your own decorations (`unicode-bidi: isolate; direction: ltr`) over `InlineCode`, `URL` and link destinations, registered through `bidiIsolatedRanges` so cursor motion matches.\[8\]
- **Gutter, vscode keymap, minimap: unverified.** In per-line mode the global editor direction stays LTR, so the gutter should stay on the left (inference). The vscode keymap maps to CM's own motion commands, which are visual and bidi-aware, but its custom commands are untested. `@replit/codemirror-minimap` draws lines to a canvas, and I found nothing showing it handles RTL. Expect RTL lines to show left-aligned or unshaped in the minimap. That's cosmetic.

**Recommended configuration (sketch):**
```js
[
  EditorView.perLineTextDirection.of(true),
  blockDirectionPlugin,      // ViewPlugin: Decoration.line({attributes:{dir}}) for visible lines only
  isolateInlineLtr,          // decorations + EditorView.bidiIsolatedRanges for InlineCode/URL/link targets
  EditorView.theme({ ".cm-line": { textAlign: "start" } })
]
```
Force fenced code block lines to `dir="ltr"`.

### 2. Deciding direction. Confidence: high on mechanics, medium on what other editors do

- **The options.** HTML `dir="auto"` maps to Unicode FSI (first-strong isolate), and `unicode-bidi: plaintext` applies the same P2/P3 rule to each paragraph.\[12\] Both pick the first strong character, so a Farsi sentence that *starts* with an English term (`React یک کتابخانه است`) resolves LTR, which is wrong. Paperling's PR handles this by skipping "markdown markers, inline code and link targets" before applying first-strong.\[6\] A 2026 bug review of another implementation found a related trap: an element with its own `dir` is a bidi-isolation boundary, so a block whose only strong text sits inside a link resolves to the inherited LTR.\[13\]
- **Recommendation: computed direction, by block, not by line.** Write one pure function, `directionOf(blockText)`. It should strip markers (`#`, `>`, list bullets, `[ ]`), inline code, URLs and link destinations, then take the first strong character. A useful stronger variant: pick RTL if the first strong character is Arabic-script, *or* if most strong characters in the first ~N words are. Apply it per markdown block: a paragraph, list item, table cell, heading or blockquote paragraph. Lines with no strong characters (blank lines, `---`, numbers, a freshly continued `- `) inherit from the enclosing block or the previous line. Provide a per-document override, using front-matter `dir: rtl|ltr|auto` or a toggle. Explicit LRM/RLM marks should be an escape hatch for edge cases, not the main mechanism.
- **Tables:** set direction for the whole table, not per cell. Obsidian RTL decides "table direction … based on the first cell".\[14\] Per-cell auto makes column order inconsistent.
- **Other editors:**
  - Obsidian added native per-line auto direction in 1.6.x. The obsidian-rtl plugin still exists because users lost the ability to force a whole file RTL (forum thread; plugin issue #83).\[15\]\[16\] Reported problems include RTL headings not aligning in auto mode (#97), Persian sentences with bold or italic English phrases getting scrambled (#77), and PDF export direction (#74).\[16\]\[17\]
  - VS Code has had issue #11770 "Support for RTL languages" open in the backlog since 2016. Its new WYSIWYG Markdown Editor is "LTR base direction" for Persian (issue #337009, 2026). The classic preview renders correct bidi order but keeps paragraphs left-aligned.\[18\]\[19\]\[20\]
  - GitHub shipped native RTL in rendered markdown (changelog 2021-11-15) and in editors (2022-01-31).\[21\]\[22\] Its known approach is per-block `dir="auto"`.\[23\]\[24\]
  - Typora, Notion and HackMD: **not verified this session.**

### 3. Preview (marked). Confidence: high for CSS mechanics, low for Mermaid

- **Direction:** use computed `dir` on each block element (`p`, `h1–h6`, `li`, `blockquote`, `table`, `th/td` inherit) from the same `directionOf`. Emit it only where it differs from the document default, as Paperling does, so "an English-only document renders and exports exactly as before".\[6\] Plain `dir="auto"` everywhere (the GitHub/markdig approach) is acceptable but fails on English-first Farsi sentences.\[24\]
- **Lists, blockquotes, tables:** bullets and numbers, blockquote borders and table column order mirror automatically under `dir="rtl"` **if** the CSS uses logical properties: `padding-inline-start`, `border-inline-start`, `margin-inline-*`, `text-align: start`. Physical `padding-left` or `border-left` is the usual bug.
- **Code:** force `pre, code { direction: ltr; unicode-bidi: isolate; }` for blocks.\[25\]\[26\] Inline code inside RTL paragraphs should be isolated, not forced to block-level LTR. One 2026 PR (openchamber) notes that this stops "an RTL opening comment" from flipping a snippet.\[7\]
- **KaTeX:** wrap rendered math in `direction: ltr; unicode-bidi: isolate`. DeepSeek's Android issue #883 shows what happens otherwise inside RTL Persian text: formulas "visually scrambled and unreadable".\[27\]
- **Mermaid:** browsers shape Arabic inside SVG correctly. The breakage reported in diagram-design issue #254 is in WeasyPrint and MuPDF, not Chrome.\[28\] Mermaid's layout direction (`LR`/`RL`) is independent of text direction, and I found no primary source on Mermaid's handling of Farsi label width or font. Set `fontFamily` in the Mermaid config to include Vazirmatn, and **test** (see Unresolved).
- **Switch to logical properties:** all list padding, blockquote border and padding, table cell alignment, footnote markers, task-checkbox margins, heading anchors, and any `float`/`left`/`right` in the preview stylesheet.

### 4. PDF via Paged.js and print. Confidence: low to medium

- Paged.js has had an RTL bug open since early on (GitHub issue #25, "pagedjs has problem with rtl direction").\[29\] I found no evidence of systematic RTL testing. The CSS Paged Media margin boxes (`@top-left`, `@bottom-right` and so on) are **physical**.\[30\] Page numbers don't mirror by themselves: for an RTL document you swap the boxes, and for facing pages use `@page :left/:right`. That is a spec fact (W3C css-page-3).\[31\]
- Mirrored margins only matter for book-style duplex output. For single-sided PDFs, symmetric margins avoid the problem completely. Push back: don't build mirroring unless someone asks for it.
- Shaping and embedding: Chrome's print-to-PDF uses the same HarfBuzz-shaped text as the screen and embeds subset fonts, so Arabic shaping should survive. **I didn't verify this for Firefox or Safari this session**, and Safari's "Export as PDF" is the one most worth testing. The real risk is mixed documents: Paged.js re-flows content into page fragments, which can split a bidi paragraph across pages. Test long mixed paragraphs that span a page break.

### 5. Fonts. Confidence: high for Vazirmatn, low for the alternatives (not checked this session)

| Font | Licence | Variable | Status | @fontsource |
|---|---|---|---|---|
| **Vazirmatn** | OFL-1.1 | Yes, `wght` 100–900, 9 weights | Upstream v33.003; npm `vazirmatn` 33.0.3, last published about 4 years ago (frozen). On Google Fonts since 2022 | `@fontsource-variable/vazirmatn` 5.3.0, subsets `arabic`, `latin`, `latin-ext`\[32\]\[33\]\[34\]\[35\] |
| Vazir Code (mono) | Conflicting: jsDelivr says "Public Domain", Bower says SAX-PD, AUR says OFL | No | **Discontinued, archived**; v1.1.2; built from Vazir + Inconsolata/Hack | No (Google Fonts request #6965 sits in backlog)\[36\]\[37\]\[38\]\[39\]\[40\]\[41\] |
| Estedad, Sahel, Shabnam, Samim, Noto Naskh/Sans Arabic | Not verified this session | — | — | — |

- **Pairing:** Vazirmatn's Latin is derived from Roboto, not Public Sans. Use only its `arabic` subset and let Public Sans render Latin, so mixed paragraphs get each script from its own family.
- **Monospace Farsi: push back on the premise.** Arabic script is joined and has very uneven natural widths. Forcing it into fixed cells (as Vazir Code does) makes it look cramped and stretched, and the only option is discontinued, with an unclear licence. jot's editor is for *prose* markdown, where column alignment only matters in code fences and pipe tables. Recommendation: `font-family: "Source Code Pro", "Vazirmatn", monospace`. Source Code Pro has no Arabic glyphs, so the browser falls back glyph by glyph. Latin and code stay monospace, Farsi is proportional, and CM6 measures real glyph positions, so cursor placement is unaffected. The cost: pipe tables with Farsi cells won't line up in the source. That's acceptable.
- **Loading:** self-host the `@fontsource-variable/vazirmatn` arabic subset only. Its `@font-face` carries a `unicode-range` covering U+0600–06FF, U+0750–077F, U+FB50–FDFF, U+FE70–FEFF, U+200C–U+200E and so on, so the file downloads only when Arabic-script text renders. Use `font-display: swap`. I didn't measure the woff2 size this session. Check it in `node_modules` after install (see Unresolved).

### 6. Persian typography. Confidence: high unless marked

- **Typing ZWNJ:** Shift+Space on Apple's Persian layouts (Apple Community). Option+Shift+Space on Persian–QWERTY gives U+202F instead.\[42\] On Windows, the "Persian (Standard)" layout (ISIRI 9147) maps ZWNJ to Shift+Space since Windows 8/8.1 updates (Behnam Esfahbod, 2014). The older "Persian" layout historically did not.\[43\] ISIRI 9147 (2007) is the national standard.\[44\] **Implication: jot must never bind Shift+Space.**
- **`highlightSpecialChars`:** CM6's default set is *not* the CM5 set. CM5's default covered `\u200b-\u200f`, which includes ZWNJ.\[45\]\[46\] My subagent couldn't retrieve CM6's current `Specials` regex verbatim, so whether ZWNJ shows as a red-dot placeholder is **unconfirmed**. Run the 30-second test in Unresolved. If it does show, configure `highlightSpecialChars({ addSpecialChars: null, specialChars: /…/ })` with a regex that excludes `\u200c` (and `\u200d`). Consider a *subtle* optional visible mark for ZWNJ as an editing aid; Persian editors like this.
- **Word counting:** ZWNJ is a format character (Cf, Join_Control).\[47\] Unicode says the joiner characters "should be ignored when determining word or line break boundaries" (quoted via Microsoft's Old New Thing).\[48\] So `می‌روم` is **one** word. Use `Intl.Segmenter(…, {granularity:'word'})` with `isWordLike`, not `split(/\s+/)`. That handles ZWNJ and Persian punctuation (، ؛ ؟). For characters, count grapheme clusters and exclude Cf format characters (ZWNJ, LRM/RLM). For paragraphs and lines, nothing changes.
- **Digits and letters:** Persian digits are ۰–۹ (U+06F0–06F9), Arabic-Indic digits are ٠–٩ (U+0660–0669), plus Latin. Arabic ي/ك vs Persian ی/ک is the main normalisation issue. **Never auto-normalise the document.** Flag it in the review (Virastar does these replacements) and normalise only for search and counting.\[49\]
- **Letter-spacing:** CSS Text 3 says that if the UA can't stretch cursive scripts properly it "must not apply spacing between any pair of that script's typographic letter units", and advises authors to avoid it.\[50\] Chromium's Intent to Ship "Ignore Letter Spacing in Cursive Scripts" covers Arabic (and therefore Persian), Hanifi Rohingya, Mandaic, Mongolian, N'Ko, Phags Pa and Syriac, and a 2026 PR states Arabic and Persian "take no letter spacing … as in Chrome since 149 and in Firefox". So the brief's "must" is already enforced by Chrome and Firefox. Still scope it yourself, for Safari (unverified) and because spacing still applies to spaces: `h1,h2,h3 { letter-spacing:-0.02em } :is(h1,h2,h3):dir(rtl) { letter-spacing: 0 }`.
- **Emphasis:** Arabic script has no italic, and Vazirmatn ships no italic, so the browser will *synthesise* a slanted fake. Recommendation (my design, not sourced): `em { font-synthesis-style: none }`, so Farsi glyphs stay upright while Public Sans keeps real italics, plus `:dir(rtl) em { font-weight: 600 }` or a colour shift so Farsi emphasis stays visible. Keep `**strong**` as weight 700/800.
- **Size and line-height:** Arabic-script text at the same font-size looks smaller and needs more vertical room for dots and diacritics. Expect to scale Vazirmatn about 5–10% via `size-adjust` on its `@font-face`, and allow line-height of about 1.7–1.8 on RTL blocks. These are typographic norms, not sourced figures; tune by eye.
- **Justification and kashida:** avoid `text-align: justify`. CSS Text says justification "must not introduce gaps between the joined typographic letter units of cursive scripts",\[50\] and browser kashida support is inconsistent. Use `text-align: start`.

### 7. Shortcuts on a Persian layout. Confidence: high for CM6, medium for raw handlers

- **CM6:** the changelog for 6.0.1 (2022-06-17) says it will "Fall back to dispatching by key code when a key event produces a non-ASCII character (so that Cyrillic and Arabic keyboards can still use bindings specified with Latin characters)". Later changes: 6.38.1 (2025-07-15) stopped key-code dispatch for macOS **Alt** combos, and 6.38.2 (2025-09-01) re-enabled it for Cmd-Alt. In the 2023 source, the fallback triggers when a character key is pressed with Alt, Meta or Ctrl, the US-layout `base[keyCode]` differs from `e.key`, and it isn't Ctrl+Alt (AltGr) on Windows. A 2026 PR in another project measured it: `key: "а", keyCode: 70 + Ctrl` (Cyrillic) fires `Mod-f`.\[4\]\[51\]\[52\]\[53\]
- **Your own `keydown` handlers:** the same PR reports that "a hand-written check for 'the F key with Cmd held' … on a Cyrillic layout … never fires".\[53\] Anything in jot that matches `e.key === 'b'` outside CM's keymap will break on Persian.
- **Fix:** route every shortcut through one matcher. Use `e.key` if it's an ASCII letter or digit; otherwise derive the letter from `e.code` (`KeyB` → `b`). Diagram-js shipped exactly this on 2026-09-30, and it only falls back when the logical key is non-Latin, so AZERTY and QWERTZ still match by logical key.\[54\] Better still, register app shortcuts as CM keymap entries where focus allows. Don't bind Shift+Space, and be careful with Option combos on macOS.

### 8. Style review in Farsi. Confidence: medium

- **Normalisation tools:** **Virastar** (brothersincode/virastar, npm `virastar` 0.22.1, updated September 2026) is a JS Persian text cleaner. Its features include Arabic kaf/yeh → Persian, Arabic and English digits → Persian, English quotes → «», Persian comma, semicolon and question mark, ZWNJ cleanup, prefix and suffix spacing (می/ها), and kashida removal.\[49\]\[55\]\[56\]\[57\]\[58\] It runs client-side. Its GitHub README states "This software is licensed under the MIT License", so it can be bundled. `persian-normalize` and `perso-match` exist for comparison-only normalisation.\[59\] Virastyar (the Word add-in) is dead (last release 2015).\[60\]
- **Style references:** the Farhangestan (Academy of Persian Language and Literature) orthography rules (دستور خط فارسی) are the authority for joining and separation (می‌، ها، ی/ئ, hamza). **I didn't fetch the primary document this session; cite it directly when you curate rules.**
- **Browser spellcheck for Persian:** not verified this session. Test it (see Unresolved), and don't build on it.
- **LLM quality:** PersLitEval (arXiv 2605.27015, May 2026; 4,514 Konkur-derived questions) shows weak grammar results: Gemini 2.5 Flash's grammar accuracy ranges only from 39.27% to 45.63% depending on prompting, and the average across models on formal linguistic categories is 32.18%. Overall, Gemini 2.5 Flash (45.07%) and GPT-4o (41.98%) lead the six models tested, GPT-4.1 Mini, Llama 3.3 70B and Qwen2.5 72B "cluster between 32–35%", and Grok 4 Fast scores lowest at 30.39%. No model reaches 50%. MELAC (arXiv 2508.00673) benchmarked 41 LLMs on 19 Persian datasets, including grammar and idioms.\[61\] **No benchmark measures style-editing quality, and PersLitEval's authors say they "were unable to evaluate additional frontier models" beyond Gemini 2.5 Flash, GPT-4o, GPT-4.1 Mini, Grok 4 Fast, Llama 3.3 70B and Qwen2.5 72B.** Implication: use the LLM for fluency and register suggestions, never as an authority on orthography. Put orthography in deterministic rules.
- **A realistic Farsi rule set:**
  - ZWNJ errors (`می روم`→`می‌روم`, `کتاب ها`→`کتاب‌ها`, `بزرگ تر`→`بزرگ‌تر`)
  - Arabic ي/ك
  - mixed digit systems within one document
  - Latin punctuation in Farsi text (`,` `;` `?`) and its spacing
  - straight quotes → «»
  - doubled spaces and spaces before punctuation
  - kashida (ـ) use
  - overuse of loanwords where a Farhangestan equivalent exists (curated list)
  - passive and long-sentence heuristics, applied with care: Persian is SOV, and English length thresholds don't carry over

### 9. UI translation and the language pack. Confidence: medium

- **i18n library:** with a menu-and-labels-sized UI, a typed dictionary plus `Intl.PluralRules`/`Intl.NumberFormat` costs about 0 KB. That's enough, since Persian plurals are simple. i18next is the heavyweight option. Lingui compiles messages at build time and is smaller at runtime. **I didn't measure bundle sizes this session.** Start with no library behind a `t()` interface you can swap later.
- **Mirroring:** set `dir="rtl"` and `lang="fa"` on `<html>` (i18next's `dir(lng)` returns `rtl` for fa, if you adopt it).\[25\] Use Tailwind v4 logical utilities (`ms-*`/`me-*`, `ps-*`/`pe-*`, `start-*`/`end-*`, `text-start`) and `rtl:` variants for one-off cases. **Keep the editor pane's global direction LTR even in an RTL UI.** Per-line direction handles content.
- **Icons:** flip directional icons (back and forward arrows, chevrons for next and previous, indent and outdent, list-bullet direction, undo and redo by convention, the sidebar-collapse arrow). Don't flip media play, checkmarks, clocks, search, brand logos or code `</>` icons.
- **Effort:** content-only Farsi is medium. A full UI mirror is medium-to-large, depending on how much physical `left`/`right` Tailwind is in the codebase; grep `ml-|mr-|pl-|pr-|left-|right-|text-left|text-right` to size it.
- **Language pack contents (proposal):**
  - `meta` (BCP-47 tag, script, default direction)
  - `detect(text)` → direction / is-this-script
  - `fonts` (`@font-face` + `unicode-range`, `size-adjust`, line-height)
  - `typography` (CSS scoped by `:lang()`/`:dir()`: letter-spacing, emphasis, justification)
  - `counting` (Segmenter locale, ignorable characters)
  - `review.rules` (regex + message + fix)
  - `review.prompt` (LLM style-guide text)
  - `ui` (string catalogue)
  - `keyboard` (reserved combos like Shift+Space)

  Keep packs data-only and lazy-loaded.

## Decisions the owner must make

1. **Translate the UI or not.** Translating doubles the QA surface: every UI change then needs RTL checks. Persian technical users generally run English UIs. My position: ship content support first and translate only if real users ask. Still build the language-pack interface so translation can come later without a refactor.
2. **Proportional vs monospace Farsi in the editor.** Monospace means a discontinued font with an unclear licence and ugly forced-width shaping. Proportional fallback means pipe tables with Farsi won't align in source. Choose proportional fallback.
3. **What emphasis looks like.** Options: upright plus heavier weight (recommended), colour, underline (it collides with links), or a synthesised slant (looks wrong to Persian readers). Decide once, put it in the pack, and render it the same way in editor, preview and PDF.
4. **Direction granularity.** Per block (recommended) or per line; whether to offer a document-level force (yes: Obsidian users demanded it after native auto shipped);\[15\] and whether English-first Farsi sentences resolve RTL by majority script (recommended) or strict first-strong.
5. **Normalisation policy.** Suggest only (recommended) or auto-fix on paste. Auto-fixing digits and ی/ک silently changes quoted Arabic text and code.

## Caveats and Unresolved (with quick tests on the M3 MacBook Pro)

- **Does CM6 `highlightSpecialChars` show ZWNJ?** Unconfirmed. Test: run `npm run dev`, switch to the macOS "Persian – Standard" input source (System Settings → Keyboard → Input Sources), type `می` then Shift+Space then `روم`. A red dot or placeholder means you need a custom `specialChars` regex. Also grep `node_modules/@codemirror/view/dist/index.js` for `Specials =`.
- **macOS Cmd+B and Cmd+Shift+V on a Persian layout in Chrome, Firefox and Safari:** log `e.key`, `e.code`, `e.keyCode` and `e.metaKey` in a document-level listener and inside CM. macOS layouts may supply a Latin "command" mapping, so `e.key` might already be Latin with Cmd held. That would make raw handlers work on Mac but still fail on Windows. Windows behaviour was not tested; the Cyrillic evidence above suggests it fails.
- **Minimap and vscode keymap with RTL lines:** paste a mixed Farsi/English document and compare Cmd+Left/Right, Alt+Left/Right word motion, and the minimap rendering.
- **Paged.js 0.4 with `dir="rtl"`:** export a 3-page mixed document with a paragraph spanning a page break, a bulleted RTL list and a table. Check page-number placement, then open the PDF in Preview and copy-paste text to confirm the Arabic characters extract in logical order. Repeat with Firefox and Safari print.
- **Mermaid Farsi labels:** render `graph RL; A[سلام]-->B[دنیا English]` in the preview and in the PDF. Check shaping, clipping of node boxes (label-width measurement before the font loads), and font.
- **Persian spellcheck:** in each browser, add `lang="fa"` and `spellcheck="true"` to the CM content and type misspellings. Chrome uses Hunspell dictionaries and macOS Safari uses the system spellchecker, but Persian availability in each was **not verified**.
- **Fonts not checked this session:** licences, weights, maintenance and woff2 sizes for Estedad, Sahel, Shabnam, Samim, Noto Naskh Arabic and Noto Sans Arabic, plus Vazirmatn's arabic-subset woff2 size. Run `npm i @fontsource-variable/vazirmatn` and `ls -l node_modules/@fontsource-variable/vazirmatn/files/*arabic*`.
